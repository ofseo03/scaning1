# 인터넷 스크린샷 100장 실사용 시험

실제로 인터넷에 올라와 있는 화면 캡처 100장을 그대로 넣어 보고, 무엇이 깨지는지
찾아 고친 기록이다. 숫자는 모두 이 저장소에서 직접 측정한 값이다.

## 어떻게 시험했나

| | |
|---|---|
| **표본** | 공개 npm 패키지에 담겨 배포된 실제 화면 캡처 100장 — 관리자 템플릿, Chrome DevTools 문서, 로그 뷰어, Swagger UI, 간트 차트, 코드 편집기, 발표 자료 등 |
| **한국어 표본** | 한글이 30자 이상 담긴 화면 17장 — 카카오 개발자 콘솔, 한국어 보고서, 한글 글꼴 견본 |
| **극단 입력** | 확장자 없는 파일, 확장자 불일치, CMYK JPEG, 16비트 회색조, 투명 PNG, 320px 축소본, 1200×12000 긴 캡처, EXIF 회전, 잘린 파일, 0바이트, 글자 없는 그림, 움직이는 GIF, 한글·공백 파일명 — 14가지 |
| **비교 기준** | 같은 그림을 `tesseract <파일> - -l kor+eng --psm 3` 로 그대로 읽은 글자 수 |
| **환경** | Ubuntu 24.04 · Python 3.11 · Tesseract 5.3.4 (kor, eng) · CPU 4코어 |
| **확인 항목** | 변환 성공 여부, 기준선 대비 글자 수, 인식 신뢰도, 회전·기울기 판정, 만들어진 docx·hwpx 의 유효성과 글자 보존, 소요 시간 |

표본은 화면 캡처의 실제 분포를 그대로 담고 있다. 100장 중 50장이 RGBA(그중 18장은
실제로 투명한 화소가 있음), 8장은 팔레트 이미지, 6장은 여러 장면이 든 GIF 이고,
크기는 640×414 부터 5472×3648 까지 걸쳐 있다.

## 결과 요약

### 스크린샷 100장

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 변환 실패 | **4장** (움직이는 GIF, 5분 초과) | **0장** |
| 글자 40% 이상 손실 | 8장 | **4장** |
| 글자 10% 이상 손실 | 15장 | **9장** |
| 멀쩡한 화면을 돌려 버림 | **10장** | **0장** |
| 인식 신뢰도 60% 미만 | 17장 | 12장 |
| 신뢰도 중앙값 | 76.9% | 78.2% |
| docx·hwpx 유효성 문제 | 0건 | 0건 |
| 100장 전체 소요 | 33분 (한 장 최대 5분+) | **13분** (한 장 최대 31초) |

파일별로는 17장이 좋아지고 8장이 나빠졌다. 나빠진 8장 중 2장은 움직이는 GIF 로,
장면 24개·7개를 모두 문서로 만들던 것이 첫 장면만 남은 결과다(의도한 변화).
나머지 6장은 -2 ~ -71자로 OCR 판정이 갈린 정도의 차이다.

글자 수만으로는 드러나지 않는 개선이 하나 더 있다. 거꾸로 뒤집혀 나오던 10장은
글자 수는 비슷했지만 내용이 알아볼 수 없는 문자열이었고, 지금은 제대로 읽힌다
(예: `a901921d9d_…_upload.png` 945자 → 920자, 신뢰도 32% → 정상).

|---|---|---|
| 멀쩡한 화면을 돌려 버림 | **5장** (29%) | **0장** |
| 인식 신뢰도 60% 미만 | 5장 | **0장** |
| 기준선 대비 글자 수(중앙값) | 1.04 | 1.03 |

### 극단 입력 14가지

확장자 없는 파일과 잘린 파일이 고쳐졌고(아래 5·6번), 움직이는 GIF 는 24쪽·34초에서
1쪽·1.6초가 됐다. 투명 배경 PNG 는 1152자·신뢰도 45% 에서 1419자·82% 로 올랐다.
나머지는 전후 모두 정상이다.

### 명령줄·웹 흐름

폴더 통째 변환(`--merge`), 같은 이름 번호 붙이기, 쪽 범위, `doctor`, `formats`,
없는 파일 오류는 모두 정상이었다. 웹 API 도 업로드 → 진행 조회 → 개별 내려받기 →
ZIP → 인식 텍스트 → 삭제까지 정상이고, `메모.txt` 업로드 거부·0바이트 거부·
잘못된 설정 JSON·`../../etc/passwd.png` 같은 이름 정리도 기대대로 동작했다.

## 찾은 문제와 고친 내용

### 1. 투명한 PNG 캡처에서 글자가 사라진다 (가장 큰 문제)

`preprocess()` 가 `img.convert("RGB")` 로 색 모드를 바꾸는데, 투명도가 있는 그림에서
이 변환은 투명한 부분의 감춰진 색(대개 검정)을 그대로 드러낸다. 창 모서리가 둥근
캡처나 그림자를 살린 PNG 는 배경이 검게 변하고, 그 위의 검은 글자가 배경에 묻힌다.

```
chrome_devtools .../primary_dodonts.png (848×1837, RGBA)
  원본 그대로                    1420자
  convert("RGB") 뒤             326자   ← 지금까지의 동작
  흰색으로 채운 뒤              1420자
  흰색으로 채우고 보정까지       1683자
```

엔진 어댑터(`ocr/tesseract.py::_save_for_ocr`)에는 흰색으로 채우는 코드가 이미
있었지만, 그 앞의 `preprocess()` 가 먼저 모드를 바꿔 버려 한 번도 쓰이지 않았다.

**고침** — `preprocess()` 맨 앞에서 투명도를 흰색으로 채운다(`flatten_alpha`).
보정을 꺼도(`--no-preprocess`) 이 단계는 거친다.

브라우저판(`public/lib/source.js`)에도 같은 문제가 있었다. PDF 를 그릴 때는
`fillRect` 로 흰 바탕을 깔면서 이미지를 그릴 때는 빈(투명한) 캔버스에 바로 그려,
회색조로 바꾸는 순간 투명한 자리가 0(검정)이 된다. 같은 방식으로 고쳤다.

### 2. 움직이는 GIF 한 장이 수백 쪽 문서가 된다

`n_frames > 1` 이면 모두 '여러 쪽'으로 보기 때문에, README 데모용 화면 녹화 GIF 가
장면 수만큼 쪽이 된다. 표본에 있던 440장면짜리 간트 차트 GIF 는 쪽마다 OCR 을 돌려
5분 제한 시간을 넘겼고(전부 돌리면 1시간 남짓), 결과물은 같은 화면이 440쪽 반복되는
문서다. 100장 중 4장이 이 때문에 실패했다.

브라우저판은 `createImageBitmap` 이 첫 장면만 읽으므로 같은 파일이 1쪽으로 나온다 —
같은 그림을 넣어도 명령줄과 웹의 결과가 달랐다.

**고침** — GIF·WEBP·APNG 처럼 움직이는 형식은 기본적으로 첫 장면만 쓴다.
여러 장이 담긴 TIFF 는 진짜 여러 쪽이므로 그대로 둔다. 모든 장면이 필요하면
`--all-frames`, 특정 장면만 필요하면 `--pages` 를 주면 된다.

### 3. 멀쩡한 화면을 거꾸로 뒤집어 놓는다

쪽 회전 감지(OSD)는 글줄이 길게 이어지는 문서를 전제로 만들어졌다. 짧은 글과 기호가
흩어진 화면 캡처에서는 판정이 사실상 동전 던지기다. 표본에서 실제로 이런 일이
일어났다.

```
똑바로 선 화면 7장에 대한 OSD 의 답            → 모두 "180도 돌아 있음"
그 7장을 일부러 180도 뒤집은 뒤 다시 물으면    → 모두 "똑바로 서 있음"
```

즉 정반대로 답한다. 그 말을 따라 뒤집힌 문서는 글자 수만 비슷할 뿐 내용은
읽을 수 없다(신뢰도 25~40%).

```
a901921d9d_react_json_editor_viewer_upload.png 의 변환 결과
  ...aqunyatduex / q / ua /svoeeezezeL/uI0/IUT “NAT -MMM//:d32y,, ...
```

수정 전 100장 중 10장, 한국어 17장 중 5장이 이렇게 뒤집혔다.

**고침** — OSD 가 회전을 말하면 그대로 믿지 않고, 작게 줄인 그림으로 후보 각도를
실제로 읽어 보고 원본보다 뚜렷하게(1.2배) 나을 때만 돌린다. OSD 가 90/270 을
뒤바꿔 말하는 경우가 있어 반대쪽도 함께 견준다.

### 4. 회색조 변환이 색으로 구분되는 글자를 지운다

`ImageOps.grayscale` 은 밝기(0.299R+0.587G+0.114B)만 남긴다. 대시보드처럼 색으로
글자와 배경을 구분하는 화면에서는 밝기 차이가 거의 없어 글자가 통째로 사라진다.

```
gentelella 관리자 템플릿 첫 화면 (2602×1336, 투명도 없음)
  원본 색 그대로            1155자
  회색조                     269자   ← 밝기만 남기면 글자가 배경에 묻힌다
  회색조 + autocontrast      269자
  색 그대로 + autocontrast  1155자
```

곁들여, `PreprocessOptions.grayscale=False` 는 실제로는 아무 일도 하지 않는다.
마지막 autocontrast 단계가 `img.convert("L")` 로 어차피 회색조로 바꾸기 때문이다.

**고침** — `grayscale=False` 가 실제로 색을 지키도록 고치고(이진화·노이즈 제거를
켠 경우에는 회색조가 필요하므로 그때만 바꾼다), 명령줄에서 쓸 수 있게
`--no-grayscale` 을 더했다.

기본값은 그대로 두었다. 100장을 회색조와 색 그대로로 각각 읽어 견줘 보니
**색이 5% 이상 나은 화면이 21장, 회색조가 나은 화면이 14장**으로 갈렸고
전체 글자 수는 67,259자 대 68,585자로 거의 같았다. 한쪽이 늘 낫지 않으므로
기본값을 뒤집을 근거가 없다고 보고, 대신 문제를 만나면 바꿀 수 있는 스위치와
안내를 README 에 넣었다.

### 5. 확장자가 없으면 열어 보지도 않고 돌려보낸다

브라우저에서 '이미지 저장'을 하면 확장자 없이(`screenshot`) 저장되는 일이 흔한데,
입력 검사가 확장자만 보기 때문에 Pillow 로 멀쩡히 열리는 파일이 거절됐다.

```
$ scan2doc screenshot
지원하지 않는 형식입니다: screenshot (지원: .bmp, .gif, .jpeg, …)
```

브라우저판은 `file.type`(MIME)도 함께 보므로 같은 파일을 받아 준다 — 여기서도
명령줄과 웹이 달랐다.

**고침** — 확장자로 알 수 없는 파일은 앞부분을 읽어 PDF 인지, Pillow 로 열리는
그림인지 확인한다. 폴더를 통째로 넣을 때는 지금처럼 확장자만 본다(엉뚱한 파일이
딸려 들어오지 않게).

### 6. 내려받다 만 그림에서 날 오류가 그대로 새어 나온다

```
OSError: image file is truncated
```

**고침** — `InputError("이미지가 손상되었거나 다 내려받지 못한 것 같습니다: …")`
로 바꿔, 무엇을 어떻게 해야 하는지 알 수 있게 했다.

### 7. 잘 되던 것들

- 만들어진 **docx·hwpx 는 96장 모두 유효**했다. ZIP 구조, XML 파싱, 필수 항목
  (`mimetype`·`version.xml`·`Contents/content.hpf`·`Contents/header.xml`)이 모두
  정상이고, **인식한 글자가 한 자도 빠지지 않고** 문서에 들어갔다.
- CMYK JPEG, 16비트 회색조 PNG, 팔레트 PNG, EXIF 회전 정보, 대문자 확장자,
  확장자 불일치(.jpg 인데 실제로는 PNG), 한글·공백·괄호가 든 파일 이름,
  1200×12000 짜리 긴 캡처, 320px 축소본, 글자가 없는 그림, 0바이트 파일 —
  모두 기대대로 처리되거나 알아들을 수 있는 오류를 냈다.
- 제목·목록 복원은 화면 캡처에서도 그럴듯하게 동작했다(전체 문단의 14%를 제목,
  2%를 목록 항목으로 판별).

## 고치지 않고 남긴 것

- **여러 단이 섞인다.** `--psm auto` 는 한 단 문서(psm 4)를 먼저 시도하는데,
  좌우로 나뉜 화면에서는 서로 다른 단의 글이 한 줄로 이어 붙는다. 한국어 문서
  사진에서는 psm 4 가 더 좋다는 판단으로 정해진 기본값이라, 화면 캡처만 보고
  바꾸지 않았다. 단이 여럿인 화면에서는 `--psm 3` 을 권한다.
- **표를 표로 살리지 못한다.** 대시보드의 표는 줄 단위 문단이 된다.
- **회전을 못 찾는 경우가 남아 있다.** OSD 가 아예 "회전 없음"이라고 답하면
  확인할 후보가 없다. 일부러 돌린 화면 캡처 21장 중 6장을 바로 세웠고,
  나머지는 원본 그대로 두었다(잘못 돌리는 일은 없어졌다).
- **긴 캡처는 느리다.** 1200×12000 짜리 한 장에 30초 안팎이 걸린다.

## 다시 돌려 보려면

이 시험에 쓴 스크립트는 저장소에 넣지 않았다. 재현하려면 화면 캡처를 한 폴더에
모아 두고 다음처럼 견주면 된다.

```bash
# 기준선: tesseract 에 그대로 넣은 결과
tesseract 화면.png - -l kor+eng --psm 3 | tr -d '[:space:]' | wc -c

# scan2doc 결과
scan2doc 화면.png -f txt -o /tmp/out
tr -d '[:space:]' < /tmp/out/화면.txt | wc -c
```

글자 수가 기준선의 60% 아래로 떨어지면 위의 1·4번 같은 문제를 의심해 볼 만하다.
